# d1-3B の Ryzen AI NPU 実装と評価

Liquid AI の判定モデル d1-3B（LFM2.5-VL-3B ベース、3.1B パラメータ）を、AMD Ryzen AI 300 シリーズ（XDNA 2）の NPU で動かした記録。言語モデルとビジョンエンコーダの両方を NPU で実行し、スループット、消費電力、精度を測定した。

測定環境：Ryzen AI 7 PRO 350（メモリ 32GB、NPU ドライバー 32.0.203.329、Windows 11 build 26200）、Ryzen AI Software 1.8.0。測定日は 2026年10月24〜25日。

## 1. 構成

| コンポーネント | 実行プロバイダ | 内容 |
|---|---|---|
| 言語モデル（デコーダ） | NPU（RyzenAILightExecutionProvider） | onnx-community の 4bit デコーダを `model_generate --npu --basic` で変換。MatMulNBits 167 ノードが NPU 演算に置換される |
| ビジョンエンコーダ | NPU（VitisAIExecutionProvider、VAIML、bf16） | SigLIP2＋プロジェクタ。入力 640×400 固定で再構成（2章） |
| トークン埋め込み | CPU | 4bit 埋め込みテーブル |

1回の推論では、状態（テキストと画像）からなる共有プレフィックスを1回だけ prefill して KV キャッシュを作り、各質問はそのキャッシュの複製から続けて評価する。質問を追加しても状態の prefill は再実行しない。

## 2. NPU 化で発生した問題と対処

### 言語モデル

- **8bit 重みは NPU に載らない。** 8bit の MatMulNBits は `--basic` の置換対象外で、`model_generate` は「No bins were filtered」を出して何も置換せず、終了コード 0 を返す。NPU カーネル名（`a16fw4acc16f`）からも重みは 4bit 固定と読める。
- **`model_generate` はエラー時も終了コード 0 を返す。** `model_generate.cli.main()` の戻り値と、変換後グラフに `com.ryzenai` 演算が含まれるかを確認する必要がある。
- **`genai-config` の値の大文字化。** CLI が値を大文字に変換する一方、内部実装は小文字を要求し、`invalid GenaiMode value: 'STANDALONE'` となる。`--extra_options genai-config=standalone` で渡すと通る。
- **最大シーケンス長。** `--basic` の出力は `hybrid_opt_max_seq_length` が 512。4096 に変更すると長いプロンプトを処理できた。値は 2 のべき乗である必要があり、3072 ではセッション作成に失敗する。
- **token fusion は使用不可。** 共有プレフィックスの KV キャッシュを複製して分岐させる方式と両立しないため、`--basic` のみを使用した。

### ビジョンエンコーダ

| 段階 | 症状 | 原因 | 対処 |
|---|---|---|---|
| セッション作成 | 1〜2.5 秒後に 0xC0000005 | 位置埋め込みの補間部で、入力 `spatial_shapes` から実行時に shape を計算する Expand。サブグラフの二分探索で特定 | 入力を 640×400（24×40＝960 パッチ）に固定し、shape 計算を定数畳み込み。com.microsoft の MultiHeadAttention 27 ノードを標準演算に分解 |
| コンパイル（既定 optimize_level 2） | aiecompiler 77-5732「Multiple tiling parameters per interleaving point」 | MLP の fc1→fc2 間の中間バッファ（960×4304、bf16 約 8MB）のタイリング。MLP 単体モデルで 35 秒で再現。中間次元を 4352 にパディングしても同じ | MLP を中間次元で 2 分割し、fc2 の部分和を加算する構成に変更。全演算が NPU の 1 サブグラフに収まる |
| optimize_level 1 | コンパイルは通るが出力が壊れる（fp32 参照とのコサイン類似度 0.02〜0.03） | optimize_level 1 では MatMul が誤った値を返す。MatMul 単体モデルで、重みや行数によらずコサイン類似度 0.70〜0.73（既定レベルでは 0.99996〜0.99998） | optimize_level 1 は使わない |

2 分割版は既定設定で 614 秒でコンパイルできた。NPU 出力と fp32 参照のコサイン類似度は 0.9957／0.9969（ログイン画面／記事画面）、1 枚あたり 0.41 秒。コンパイル結果はキャッシュされ、2 回目以降は即座にロードされる。

### その他

- **DirectML（ORT 1.27）では GQA 内の RoPE が適用されない。** `do_rotary=1` が反映されず、回転位置埋め込みなしで計算される。RoPE をグラフ上で明示的な演算に分離すると CPU と一致した。
- **分割後の MLP の GELU は厳密形。** 元モデルの GELU は tanh 近似（`approximate="tanh"`）だが、分割時に再生成した GELU ノードはこの属性を引き継いでおらず、erf による厳密形で計算する。CPU 上での元のビジョンエンコーダとのコサイン類似度は 0.99998。5〜7章の測定はすべてこのモデルで行った。
- **4bit ビジョンエンコーダは精度が落ちる。** 画像特徴の fp32 参照とのコサイン類似度は 0.946〜0.961 で、判定結果が変わるケースがあった。ビジョンエンコーダは fp32 重みのまま NPU（bf16）で実行した。

## 3. 精度（公式 fp32 実装との比較）

テキスト 3 件（返金依頼、雑談、計測障害の報告）と画像 2 枚（ログイン画面、記事画面）に対する計 27 問で、公式の transformers 実装 fp32（CPU）を参照とした。

| 構成 | 選択の一致 | 確率差 0.05 以内 | 最大確率差 |
|---|---|---|---|
| NPU 言語モデル＋NPU ビジョン | 27/27 | 21/27 | 0.130 |
| NPU 言語モデル＋CPU ビジョン（8bit） | 27/27 | 20/27 | 0.134 |
| llama.cpp（GGUF、GPU） | 27/27 | 25/27 | 0.135 |
| CPU 8bit（参照に最も近い量子化） | 27/27 | 27/27 | 0.027 |

## 4. スループットと消費電力

同じ 27 問を、毎回ビジョンエンコーダから再実行して約 2 分間連続で処理した。アイドル時との差分を、Windows の Energy Meter（APU・CPU・GPU・NPU の電力）と GPU Engine の使用率で測定した。

| 構成 | 判定/秒 | CPU 使用率（差分） | GPU 使用率 | NPU 電力 | APU 電力（差分） | 1判定あたりのエネルギー |
|---|---|---|---|---|---|---|
| GPU（llama.cpp、Vulkan） | 2.45 | −10.6 | 35% | 0 | +8.9W | 3.62J |
| NPU 言語モデル＋CPU ビジョン | 2.10 | +24.7 | 0% | 0.73W | +7.1W | 3.38J |
| **NPU 言語モデル＋NPU ビジョン** | **3.51** | −1.1 | 0% | 0.92W | +3.9W | **1.11J** |

CPU 使用率の差分には数ポイントの変動が含まれる（他のアプリケーションの影響でアイドル時の使用率が高かった回がある）。

## 5. 実ブラウザ画面での評価

ブラウザ操作エージェントの補助として、画面状態を判定させる用途を想定し、実画面 100 枚で評価した。

- データセット：IT 事務職系ツールの画面 78 枚と、公開サイト 22 枚（11 サイトを 1280×800 と 1920×1080 で撮影。ログイン画面、記事、検索結果、エラーページなど）。
- 質問：ログインフォームの有無、画面種別、エラー表示、ダイアログ、読み込み中、ログイン時の次の操作対象、CAPTCHA、数値テーブル、日付ピッカー、ドロップダウンメニューの 10 問。正解ラベルは目視で付与し、判断が分かれるものは採点対象外とした（採点対象 919 問）。
- NPU 版は画像を 640×400 にリサイズして入力する。公式実装はネイティブ解像度のまま、512×512 のタイルとサムネイルに分割して入力する（画像トークン数の中央値は 765、NPU 版は 240）。

| 構成 | 正解率（100 画面） | 1 画面あたりの処理時間（12 問で測定） |
|---|---|---|
| 公式 fp32・ネイティブ解像度 | 78.8% | 52 秒（CPU） |
| 公式 fp32・640×400 | 76.8% | 28 秒（CPU） |
| NPU・640×400（アスペクト比を無視してリサイズ） | 75.8% | 5.1 秒 |
| NPU・640×400（レターボックス） | 74.9% | 5.5 秒 |

ダウンサンプリングによる低下が約 2 ポイント、NPU 化による低下が約 1 ポイント。ダウンサンプリングで誤りが増えるのは主に画面種別で、テキスト量の多いドキュメントページをツール画面と判定するケース。NPU 版の処理時間は、公式実装の CPU 推論と並行実行した条件での値。

### API 提供の判定モデルとの比較（公開サイト 22 枚）

公開サイト 22 枚・10 問（採点対象 208 問）を、OpenRouter の Decisions API にネイティブ解像度で入力した。

| モデル | 正解率 | 1 画面あたりの処理時間（12 問、通信込み） |
|---|---|---|
| d1 Ultra（liquid/d1-ultra） | 100% | 0.9 秒 |
| d1（liquid/d1） | 99.0% | 1.1 秒 |
| Jev 1.14 | 99.0% | 0.4 秒 |
| GPT-6 Luna Decisions | 98.1% | 0.8 秒 |
| d1-3B 公式 fp32・ネイティブ解像度 | 79.3% | 59 秒（CPU） |
| d1-3B NPU・640×400（ベースラインのプロンプト） | 76.4% | 6.0 秒 |

API の `liquid/d1` は公開されている d1-3B とは別のモデル（テキストのみの質問でも確率が一致しない）。

## 6. プロンプトと判定閾値の調整

NPU 版のまま、プロンプトと二値判定の閾値だけを変更した。100 画面をファイル名のハッシュで調整セット（59 画面）と検証セット（41 画面・384 問）に分け、プロンプトと閾値は調整セットだけで選び、検証セットで評価した。

| プロンプト | 検証セットの正解率 |
|---|---|
| ベースライン | 77.3% |
| 日本語＋判定基準（選択肢に説明を付与） | 87.2% |
| 英語（判定基準なし） | 74.5% |
| 英語＋判定基準 | 85.2% |
| 公開プリセット（質問ごとにプロンプトと閾値を選択、`d1npu/screen_check.json`） | **95.8%** |

公開プリセットは、状態テキストと画面種別の選択肢説明 1 件が他の行と異なる。公開サイト 22 枚だけでは、ベースライン 76.4%、公開プリセット 95.2%（22 枚の一部は調整セットに含まれる）。

- **質問に条件を明記する。** ログイン時の次の操作対象は、「ログイン画面でない場合は other」と明記し、選択肢に「空欄の場合」などの条件を付けると、正解率が 19% から 97% に上がった。
- **二値判定に判定基準を付ける。** 「期間表示ボタンや日付テキストのみの場合は含めない」のように除外条件を書くと、偽陽性が減る。
- **閾値を上げる。** d1-3B は yes に偏る傾向があり、誤りはすべて偽陽性だった。閾値を 0.5 から 0.6〜0.95 に上げるだけで大きく改善する（ダイアログはベースラインのプロンプトのままで 22/32 → 31/32）。
- **質問だけを英語にすると精度が下がる。** 画面と状態テキストが日本語のため、CAPTCHA などで低下した。

## 7. 不向きな用途：候補リストからの次操作の選択

ブラウザ操作の補助ツール（画面上の操作候補を最大 56 個収集し、判定モデルに次の 1 つを選ばせて親エージェントを介さずに進める制御プログラム）が、読み取り専用タスクで行った 130 回の判断を実行ログから再構成し、各判定モデルに入力した。入力は画像なしのテキストのみで、1 問あたり中央値 1,600 トークン。選ばれた操作の妥当性は、どのモデルの出力かを伏せて判定した。

| モデル | 妥当な操作の選択率 | 1 回あたりの処理時間 |
|---|---|---|
| d1 Ultra（API） | 93.1% | 0.53 秒 |
| Jev 1.14（API） | 80.8% | 0.36 秒 |
| d1（API） | 80.0% | 0.50 秒 |
| GPT-6 Luna Decisions（API） | 66.9% | 0.43 秒 |
| d1-3B NPU | 40.0% | 3.37 秒 |
| d1-3B NPU・短縮プロンプト（状態約 300 トークン、候補を短い日本語に） | 36.9% | 1.69 秒 |
| d1-3B NPU・上位 10 候補に絞り、候補ごとに二値判定 | 45.4% | 3.28 秒 |

公式 fp32 実装でも同じ 29 問で 14/29（NPU 版 13/29）であり、NPU 化ではなく 3B モデル自体の能力の限界。長い候補リストからの選択には向かず、画面状態の二値判定に向いている。
