# d1-3B を Ryzen AI NPU で動かした記録

Liquid AI の判定モデル d1-3B（LFM2.5-VL-3B ベース、3.1B）を、AMD Ryzen AI 300 シリーズの NPU で動かした実験の記録。言語部分と画像の読み取り部分の両方を NPU に載せ、速さ・電力・判定の正しさを測った。

測定機：Ryzen AI 7 PRO 350（メモリ32GB、NPU ドライバー 32.0.203.329、Windows 11 build 26200）、Ryzen AI Software 1.8.0。測定日は2026年10月24〜25日。

## 1. 構成

| 部分 | 実行先 | 中身 |
|---|---|---|
| 言語部分 | NPU（RyzenAILightExecutionProvider） | onnx-community の 4bit デコーダを `model_generate --npu --basic` で変換。167個の MatMulNBits が NPU 演算に置き換わる |
| 画像の読み取り部分 | NPU（VitisAIExecutionProvider、VAIML、bf16） | SigLIP2＋射影。640×400 固定に作り直したもの（2章） |
| 単語の埋め込み | CPU | 4bit の埋め込み表 |

1回の判定は、状態（文と画像）を1回だけ読んで KV キャッシュを作り（幹）、問いごとにその写しから続きを読む（枝）。問いを足しても状態は読み直さない。

## 2. NPU に載せるまでに当たった問題

### 言語部分

- **8bit の重みは NPU に載らない。** 8bit の MatMulNBits は `--basic` の置き換え対象外で、`model_generate` は終了コード0でも「No bins were filtered」で何も置き換えない。NPU 部品名（`a16fw4acc16f`）からも、重み4bit 固定と読める。
- **`model_generate` はエラーでも終了コード0を返す。** `model_generate.cli.main()` の戻り値を見て、変換後のグラフに `com.ryzenai` の演算があるかを確かめる必要がある。
- **`genai-config` の値の大文字化。** 入口が値を大文字にする一方、内部は小文字を要求して `invalid GenaiMode value: 'STANDALONE'` になる。`--extra_options genai-config=standalone` で渡すと通る。
- **一度に読める長さ。** `--basic` の変換結果は `hybrid_opt_max_seq_length` が512。4096 に書き換えると長い問いも読めた。値は2のべき乗でないとセッション作成で失敗する（3072 は不可）。
- **token fusion は使えない。** 幹・枝方式の途中状態が壊れるため、`--basic` だけを使った。

### 画像の読み取り部分

| 段階 | 症状 | 原因 | 対処 |
|---|---|---|---|
| セッション作成 | 1〜2.5秒で 0xC0000005 | 位置埋め込みの補間部で、入力 `spatial_shapes` から実行時に形を計算する Expand。部分モデルの二分探索で特定 | 入力を 640×400（24×40＝960パッチ）に固定し、形の計算を定数に畳み込む。com.microsoft の MultiHeadAttention 27個は標準演算に分解 |
| コンパイル（既定 optimize_level 2） | aiecompiler 77-5732「Multiple tiling parameters per interleaving point」 | MLP の fc1→fc2 の中間バッファ（960×4304、bf16 約8MB）の区切り方。MLP だけのモデルで35秒で再現。中間幅を4352にしても同じ | MLP を中間の幅で2分割し、fc2 の部分和を足す形にする。全演算が NPU の1サブグラフになる |
| optimize_level 1 | コンパイルは通るが出力が壊れる（公式とのコサイン類似度 0.02〜0.03） | optimize_level 1 の行列積が誤った値を返す。行列積1個のモデルで、重みや行数によらず 0.70〜0.73（既定は 0.99996〜0.99998） | optimize_level 1 は使わない |

2分割版は既定の設定で614秒でコンパイルでき、NPU の出力と公式 fp32 のコサイン類似度は 0.9957／0.9969（ログイン画面／記事の画面）、1枚 0.41秒。コンパイル結果はキャッシュされ、2回目からはすぐ読み込める。

### そのほか

- **DirectML（ORT 1.27）では GQA の RoPE が抜ける。** `do_rotary=1` が反映されず、位置の回転なしで計算される。RoPE をグラフの外で明示すると CPU と一致した。
- **分割した MLP の GELU は正確な式になっている。** 元のモデルは近似式（`approximate="tanh"`）だが、分割で作り直した GELU にはこの指定を引き継いでおらず、正確な式（erf）で計算する。CPU で比べると、元の画像部分とのコサイン類似度は 0.99998。5〜7章の測定もこの形のモデルで行った。
- **4bit の画像部分は精度が落ちる。** 画像の埋め込みの公式とのコサイン類似度は 0.946〜0.961 で、判定が変わる例があった。画像部分は fp32 の重みのまま NPU（bf16）に載せた。

## 3. 正しさ（公式 fp32 との比較）

文の判定3件（返金の依頼、雑談、計測の障害の報告）と画面2枚（ログイン画面、記事）に、計27問。公式の transformers 版 fp32（CPU）を基準にした。

| 構成 | 選択の一致 | 確率の差0.05以内 | 最大差 |
|---|---|---|---|
| NPU 言語＋NPU 画像 | 27/27 | 21/27 | 0.130 |
| NPU 言語＋CPU 画像（8bit） | 27/27 | 20/27 | 0.134 |
| llama.cpp（GGUF、GPU） | 27/27 | 25/27 | 0.135 |
| CPU 8bit（基準に一番近い量子化） | 27/27 | 27/27 | 0.027 |

## 4. 速さと電力

同じ27問を、毎回画像の読み取りからやり直して約2分続けた。何もしない状態との差を、Windows の Energy Meter（APU・CPU・GPU・NPU の電力）と GPU Engine の使用率で測った。

| 構成 | 1秒あたりの判定 | CPU 使用率（増分） | GPU 使用率 | NPU 電力 | APU 電力（増分） | 1判定あたり |
|---|---|---|---|---|---|---|
| GPU（llama.cpp、Vulkan） | 2.45 | −10.6 | 35% | 0 | +8.9W | 3.62J |
| NPU 言語＋CPU 画像 | 2.10 | +24.7 | 0% | 0.73W | +7.1W | 3.38J |
| **NPU 言語＋NPU 画像** | **3.51** | −1.1 | 0% | 0.92W | +3.9W | **1.11J** |

CPU 使用率の増分は ±数ポイントの揺れを含む（何もしない状態の使用率がほかのアプリで高かった回がある）。

## 5. 実際のブラウザ画面での判定

ブラウザ操作をするエージェントの横で「いま画面がどういう状態か」を答えさせる使い方を想定して、実際の画面100枚で測った。

- 画面：IT 事務職系ツールの画面78枚と、公開サイト22枚（11サイトを 1280×800 と 1920×1080 で撮影。ログイン画面、記事、検索結果、エラー画面など）。
- 問い：ログイン入力欄の有無、画面の種類、エラー表示、ダイアログ、読み込み中、ログインの次の操作、ロボット確認、数値の表、日付パネル、メニュー、の10問。正解は画面を見て付け、判断が割れるものは採点しない（採点できる問い 919）。
- NPU 版は画像を 640×400 に縮めて読む。公式は元の大きさのまま、512四方の区画と全体の縮小図に分けて読む（画像トークン中央値765、NPU 版は240）。

| 構成 | 正解率（100画面） | 1画面の時間（12問で測定） |
|---|---|---|
| 公式 fp32・元の大きさ | 78.8% | 52秒（CPU） |
| 公式 fp32・640×400 | 76.8% | 28秒（CPU） |
| NPU・640×400（伸縮） | 75.8% | 5.1秒 |
| NPU・640×400（黒帯を付けて縮小） | 74.9% | 5.5秒 |

縮小による低下が約2ポイント、NPU 化による低下が約1ポイント。縮小で間違えやすくなるのは主に「画面の種類」（文字の多い文書ページを、ツールの画面と答える）。NPU 版の時間は、公式の CPU 実行と同時に動かしたときのもの。

### API で提供されている判定モデルとの比較（公開サイト22枚）

公開サイトの22枚・10問（採点できる問い 208）を、OpenRouter の判定 API で元の大きさのまま問うた。

| モデル | 正解率 | 1画面の時間（12問、通信込み） |
|---|---|---|
| d1 Ultra（liquid/d1-ultra） | 100% | 0.9秒 |
| d1（liquid/d1） | 99.0% | 1.1秒 |
| Jev 1.14 | 99.0% | 0.4秒 |
| GPT-6 Luna Decisions | 98.1% | 0.8秒 |
| d1-3B 公式 fp32・元の大きさ | 79.3% | 59秒（CPU） |
| d1-3B NPU・640×400（最初の書き方） | 76.4% | 6.0秒 |

API の `liquid/d1` は公開版の d1-3B とは別のモデル（文だけの問いでも確率が合わない）。

## 6. 問いの書き方と「はい」の境目

NPU 版のまま、問いの書き方と「はい」と判定する境目だけを変えた。100画面を名前で2つに分け、書き方と境目は片方（59画面）で決め、もう片方（41画面・384問）で測った。

| 書き方 | 確かめる側の正解率 |
|---|---|
| 最初の書き方 | 77.3% |
| 日本語＋はい/いいえの基準（選択肢には説明） | 87.2% |
| 英語（基準なし） | 74.5% |
| 英語＋基準 | 85.2% |
| 問いごとに選んだ書き方＋境目（`d1npu/screen_check.json`） | **95.8%** |

最後の行は公開した問いのセットそのもので測った。状態の文と、画面の種類の選択肢の説明1つが、ほかの行と違う。

公開サイトの22枚だけで見ると、最初の書き方 76.4% → 公開した問いのセット 95.2%（22枚の一部は書き方を選ぶ側に入っている）。

- **問いに条件を書く。** 「ログインするために次に操作すべきもの」は、「ログイン画面でなければ『それ以外』」と書き、選択肢に「空欄のとき」などの条件を付けると、19%から97%になった。
- **はい/いいえに基準を付ける。** 「期間を表示するボタンや日付の文字だけの場合は含めない」のように、含めないものを書くと「ある」と答えすぎるのが減る。
- **境目を上げる。** d1-3B は「はい」に寄りやすい。外した画面はすべて「無いのに『ある』」だった。境目を 0.5 から 0.6〜0.95 に上げるだけで大きく直る（ダイアログは最初の書き方のままでも 22/32 → 31/32）。
- **問いだけ英語にすると下がる。** 画面と状態の文が日本語なので、ロボット確認などが落ちた。

選んだ書き方と境目は `d1npu/screen_check.json`。

## 7. 不得意な使い方：候補一覧から次の操作を選ぶ

ブラウザ操作の補助ツール（画面の操作候補を最大56個集め、判定モデルに次の1つを選ばせて親エージェントに戻らずに進める制御プログラム）が、読み取り専用の課題で出した判断130回を記録から組み直し、判定モデルに答えさせた。問いは画像なしの文だけで、1問あたり中央値1,600トークン。選ばれた操作の妥当さは、どのモデルの選択かを伏せて判定した。

| モデル | 妥当な操作を選んだ | 1回の時間 |
|---|---|---|
| d1 Ultra（API） | 93.1% | 0.53秒 |
| Jev 1.14（API） | 80.8% | 0.36秒 |
| d1（API） | 80.0% | 0.50秒 |
| GPT-6 Luna Decisions（API） | 66.9% | 0.43秒 |
| d1-3B NPU | 40.0% | 3.37秒 |
| d1-3B NPU・短い問い（状態約300トークン、候補を短い日本語に） | 36.9% | 1.69秒 |
| d1-3B NPU・候補を上位10個に絞り、1つずつはい/いいえ | 45.4% | 3.28秒 |

公式 fp32 でも同じ29問で 14/29（NPU 13/29）なので、NPU 化ではなく 3B モデルの力の問題。長い候補一覧から1つ選ぶ使い方には向かず、画面の状態をはい/いいえで確かめる使い方に向いている。
